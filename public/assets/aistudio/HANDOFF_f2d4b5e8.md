# Hosts Blocker — техническая передача проекта другому ИИ-агенту

Этот файл адресован ИИ-агенту (например, другой модели в Google AI Studio или
аналогичном инструменте), который продолжит разработку. Он написан не для
конечного пользователя программы, а для разработчика/агента, который будет
читать и менять код.

Программа написана человеком-непрограммистом в диалоге с ИИ-ассистентом
(Claude), итеративно, патч за патчем. Код рабочий и протестирован в той мере,
в какой это возможно без Windows-машины (см. раздел «Как это тестировалось»),
но не проходил полный профессиональный аудит. Если ты — следующий агент,
относись к коду критически, а не как к эталону.

## 0. Что это и для кого

Windows-приложение родительского контроля для **собственного ребёнка
пользователя**, на **его же домашнем компьютере**. Все функции — локальная
блокировка, чтение заголовков окон, отключение Windows-аккаунта — выполняются
с ведома и по инициативе родителя-администратора, защищены паролем. Это не
инструмент скрытого наблюдения за посторонними людьми. При доработке держи
эту рамку: не добавляй скрытность от родителя, не ослабляй требование пароля,
не добавляй функции, которые могли бы использоваться для слежки за кем-то без
его ведома за пределами этого сценария «родитель — несовершеннолетний ребёнок
на домашнем ПК».

## 1. Формат поставки: один файл

Вся программа — один файл `hosts_blocker.py` (~2400 строк, ~370 КБ, т.к. в
конце файла встроены PNG-картинки логотипов в виде base64-строк). **Это
осознанное требование пользователя**: без внешних зависимостей (кроме
стандартной библиотеки Python), чтобы не ловить ошибки вроде `ModuleNotFoundError:
No module named 'PIL'` при сборке в exe через PyInstaller. Если будешь
добавлять функциональность — старайся не вводить pip-зависимости. Если без
них никак, явно предупреди пользователя и объясни, что придётся менять
процесс сборки.

Пользователь собирает exe сам, подробности — в разделе 1.1.

### 1.1. Как собирается .exe

Одна команда превращает весь `hosts_blocker.py` в один `.exe`-файл:
```
pip install pyinstaller
pyinstaller --onefile --noconsole hosts_blocker.py
```
Готовый файл появляется в `dist\hosts_blocker.exe`. Больше ничего собирать
не нужно: никакого отдельного `engine.exe` или `agent.exe` не существует —
это **один и тот же exe**, который движок и агент запускают сам на себя с
аргументом `--engine` или `--agent` (раздел 2.1–2.3, `engine_command()`
копирует именно этот exe в `BIN_DIR` и далее через `schtasks`/автозапуск
стартует его же с этим аргументом). Если меняешь имя файла или схему сборки
— не забудь, что `engine_command()` формирует команду запуска исходя из
`sys.executable`/`__file__`, и там же завязан на то, что PyInstaller даёт
`sys.frozen = True` у собранного exe (см. `if getattr(sys, "frozen",
False):`) — это определяет, копируется ли сам exe или питоновский скрипт
вместе с путём к `pythonw.exe`.

Важные флаги:
- **Без `--uac-admin`.** Если его добавить, Windows будет спрашивать
  подтверждение администратора при **каждом** запуске exe — включая
  автозапуск `--agent` при входе любого пользователя в систему, что для
  ребёнка означало бы окно UAC при каждом входе в Windows. Вместо этого
  программа сама вызывает `relaunch_as_admin()` (через `ShellExecuteW` с
  `"runas"`) только при запуске без аргументов (то есть только когда
  родитель открывает окно GUI) — `--engine` и `--agent` этот путь не
  проходят и UAC не вызывают.
- **`--noconsole`.** Прячет консольное окно — у программы нет вывода в
  консоль, весь лог идёт в `error.log` (`log_error()`), а ошибки
  показываются через `messagebox`/`MessageBoxW`.
- **`--onefile`** — обязателен, чтобы получить один exe без рядом лежащей
  папки с DLL/зависимостями (соответствует требованию «один файл», раздел 1).

Если следующий агент добавит pip-зависимость (раздел 4.3 — например, ради
видеопотока) — после этого сборка **обязательно** должна тестироваться
заново: PyInstaller иногда не подхватывает нестандартные зависимости
автоматически, и придётся добавлять `--hidden-import` или `.spec`-файл.

## 2. Как всё устроено: три режима запуска одного файла

Это не три файла и не служба Windows в классическом смысле (не
`sc create`), а **один .py/.exe**, который ведёт себя по-разному в
зависимости от аргумента командной строки. Точка входа — самый конец файла:

```python
if __name__ == "__main__":
    if "--engine" in sys.argv:
        engine_main(); sys.exit(0)
    if "--agent" in sys.argv:
        agent_main(); sys.exit(0)
    if not is_admin():
        relaunch_as_admin()
    enable_dpi()
    App().mainloop()
```

### 2.1. Окно (без аргументов) — `class App(tk.Tk)`
Запускается пользователем (администратором) вручную. Просит права
администратора через UAC (`relaunch_as_admin()`), поднимает tkinter-GUI:
вход по паролю → список записей с переключателями → диалоги редактирования.
При первом успешном входе само разворачивает фоновую часть
(`ensure_background()` → `install_background()`), см. раздел 2.2.

### 2.2. Движок (`--engine`) — `engine_main()` / `engine_tick(st)`
Работает **от имени SYSTEM**, без окна, без интерактивного рабочего стола.
Запускается через задачи Планировщика заданий Windows (не через `sc`/службу
Windows — так было проще реализовать без доп. зависимостей и без написания
Windows Service wrapper'а). Две задачи создаются через `schtasks`:
- `HostsBlockerEngine` — `/SC ONSTART`, запускается при загрузке системы;
- `HostsBlockerWatchdog` — `/SC MINUTE /MO 5`, перезапускает движок, если тот
  упал (просто пытается запустить ту же команду каждые 5 минут; если
  `single_instance()` уже держит мьютекс, новый процесс тихо завершится).

Копия программы для движка лежит в `C:\ProgramData\HostsBlocker\bin` с ACL
«только Администраторы/SYSTEM» (`engine_command()`), чтобы обычный
пользователь (ребёнок) не мог её подменить или удалить.

`engine_tick(st)` вызывается в цикле `while True: ...; time.sleep(TICK)` с
`TICK = 2` секунды. На каждом тике:
1. Перечитывает `config.json`, если изменился `mtime` (значит, кто-то —
   GUI или веб-панель — сохранил новые настройки).
2. Обрабатывает `reset.json` (запрос сброса счётчика времени от GUI/панели).
3. Если сутки сменились — обнуляет счётчики «за сегодня».
4. `procs = running_names()` (через `tasklist`), `agents = fresh_agents()`
   (читает `agent_*.json` из `PUB_DIR`, см. 2.3, считает «свежими» записи не
   старше 10 секунд).
5. Если агент активен — копит секунду «компьютерного времени»
   (`u["today"]["__computer__"]`) для лимита полной блокировки.
6. Считает `full_blocked(cfg, u)` — нужна ли полная блокировка компьютера; при
   смене состояния вызывает `apply_full_lock()` (раздел 2.5).
7. Для каждой записи с лимитом, которая реально используется прямо сейчас
   (`in_use()` — процесс запущен ИЛИ заголовок активного окна браузера
   содержит одно из ключевых слов записи), прибавляет время использования.
8. Пересчитывает «эффективный» список (`effective(entries, u)` — какие записи
   реально должны быть заблокированы прямо сейчас с учётом лимитов) и, если
   он изменился, заново применяет `apply_hosts` / `apply_browser_policies` /
   `apply_firewall` (функция `apply_all`).
9. Для включённых записей со способом «kill» — закрывает запущенные процессы
   (`kill_processes`).
10. Обновляет `blocked.json` в `PUB_DIR` — список ключевых слов для агента,
    чтобы тот знал, какие вкладки закрывать (см. 2.3).
11. `panel_sync(st)` — поднимает/останавливает HTTP-сервер веб-панели, если
    настройка `cfg["web"]["enabled"]` изменилась (раздел 2.6).
12. Раз в 10 секунд сохраняет `usage.json` на диск (не на каждый тик, чтобы
    не дёргать диск).

### 2.3. Агент (`--agent`) — `agent_main()`
Запускается **в сеансе каждого пользователя** (через автозапуск
`HKLM\...\Run`, ключ `RUN_NAME = "HostsBlockerAgent"` — да, в `HKLM`, не в
`HKCU`, чтобы один раз прописать на всех пользователей; это требует прав
администратора на момент установки, что есть, т.к. ставит его GUI,
запущенный с правами администратора). Нужен, потому что движок (SYSTEM) **не
видит** рабочий стол и активное окно пользователя — у Windows разделены
сеансы (Session 0 isolation).

Что делает каждую секунду:
1. `foreground_info()` — через WinAPI (`GetForegroundWindow`,
   `GetWindowTextW`, `QueryFullProcessImageNameW`) узнаёт заголовок и имя
   процесса активного окна.
2. Копит секунды в `proc_sec` / `title_sec` (для функции «Активность»,
   раздел 2.7) и каждые 5 секунд сбрасывает это в `activity_<user>.json`.
3. Пишет своё текущее состояние в `agent_<user>.json` (это и есть «пульс»,
   по которому движок узнаёт, что пользователь активен — см. `fresh_agents()`
   в движке).
4. Читает `blocked.json` (пишет движок) — список ключевых слов
   заблокированных сайтов. Если заголовок активного окна браузера содержит
   одно из них — эмулирует Ctrl+W (`close_tab()`, через `keybd_event`),
   закрывая вкладку. Не чаще раза в 3 секунды, чтобы не спамить.

Все файлы агента лежат в `PUB_DIR` = `C:\ProgramData\HostsBlockerPub` с ACL
«встроенная группа Users может писать» (`ensure_pub_dir()`), т.к. это
единственный способ обмена данными между сеансом SYSTEM (движок) и сеансом
обычного пользователя (агент) без полноценного IPC. **Из этого вытекает
ограничение**: обычный пользователь технически может сам отредактировать или
удалить эти файлы (например, `activity_<user>.json`), и движок/GUI этого не
заметят — отчёт просто будет неполным. Это сознательно принятый компромисс
ради простоты (см. раздел 5, пункт про это).

### 2.4. Межпроцессный обмен — файлы, не IPC/сокеты
Весь обмен между GUI, движком и агентом идёт через файлы в двух папках:
- `C:\ProgramData\HostsBlocker` (`CONF_DIR`) — закрыта для обычных
  пользователей (`secure_conf_dir()`, ACL только Admins+SYSTEM). Здесь:
  `config.json` (пароль-хэш + список записей + настройки), `usage.json`
  (накопленное время использования), `reset.json` (временный файл-сигнал
  «сбросить счётчик»), `error.log`, `bin/` (копия программы для движка),
  `icons/` (кэш скачанных фавиконок).
- `C:\ProgramData\HostsBlockerPub` (`PUB_DIR`) — открыта для записи обычным
  пользователям (ACL Users:Modify). Здесь: `agent_<user>.json` (пульс
  агента), `activity_<user>.json` (накопленная активность), `blocked.json`
  (ключевые слова для закрытия вкладок, пишет движок, читает агент).

Все записи в оба файла атомарные: пишется `*.tmp`, потом `os.replace()` —
это гарантирует, что читающая сторона никогда не увидит повреждённый
наполовину записанный JSON. **Если будешь добавлять новые файлы обмена —
следуй этому же паттерну** (временный файл + `os.replace`).

Эта файловая архитектура — самое уязвимое место для багов типа «гонка
данных», если решишь расширять. Полноценных блокировок между процессами нет
(кроме `PANEL_LOCK` внутри процесса движка для веб-панели, раздел 2.6) —
рассчитано на то, что конфликты редки (пользователь обычно одно действие за
раз), а атомарная запись файлов не даёт им испортиться, просто одно
изменение может быть перезаписано другим, если они случились в одну-две
секунды. Для прод-уровня стоило бы продумать это серьёзнее (блокировки,
версионирование, честный merge).

### 2.5. Полная блокировка компьютера/аккаунта — `full_blocked`, `apply_full_lock`
Данные: `cfg["child_account"]` (строка — системное имя Windows-аккаунта
ребёнка, пользователь вводит вручную через GUI, есть кнопка «показать список
учётных записей» — запускает `net user` и показывает вывод) и
`cfg["full_lock"]` = `{"now": bool, "daily": int, "total": int, "from": str,
"to": str}` (структура как у лимита отдельной записи, см. 2.8).

`full_blocked(cfg, u)` — чистая функция, считает, должен ли компьютер быть
заблокирован прямо сейчас (ручной флаг `now`, либо превышен дневной/общий
лимит «компьютерного времени» `u["today"/"total"]["__computer__"]`, либо
сейчас не входит в разрешённое окно времени).

`apply_full_lock(username, locked)` — **единственное место, где программа
реально воздействует на систему сильнее, чем блокировка сети**:
- `set_account_active(username, not locked)` → `net user <имя> /active:no`
  — Windows отказывает в новом входе в систему под этим аккаунтом.
- если `locked=True`, также `logoff_user_sessions(username)` — через
  `wtsapi32.dll` (`WTSEnumerateSessionsW` + `WTSQuerySessionInformationW` +
  `WTSLogoffSession`) находит все активные сеансы этого пользователя и
  принудительно завершает их (как «Выйти», только без спроса).

Важно понимать, **почему не просто `LockWorkStation()`** (запереть экран):
ребёнок, знающий свой пароль Windows, снимет блокировку экрана за секунду.
Отключение аккаунта + принудительный логофф — единственный способ реально
закрыть доступ средствами самой Windows без установки драйверов/сервисов.
**Это не протестировано на реальной Windows-машине** (в песочнице, где
писался код, Windows недоступна) — следующему агенту стоит в первую очередь
проверить именно эту часть (права SYSTEM на `WTSLogoffSession`, корректность
структур ctypes, поведение `net user` на разных локализациях Windows).

### 2.6. Веб-панель (управление с телефона по Wi-Fi)
Включается через GUI (кнопка «📱 Панель» → чекбокс → порт). Настройка
хранится в `cfg["web"] = {"enabled": bool, "port": int}`. Поднимается и
останавливается самим движком (`panel_sync(st)` в `engine_tick`), не
отдельным процессом.

Реализация — `http.server.ThreadingHTTPServer` + `PanelHandler
(BaseHTTPRequestHandler)`, без Flask/FastAPI (опять же — без зависимостей).
Отдаёт одну HTML-страницу с инлайн-JS (строка `PANEL_HTML`, обычный
fetch()-based SPA без фреймворков) и JSON API:
- `POST /api/login {password}` → куки-сессия (`hb_session`, HttpOnly,
  SameSite=Strict, 12 часов). Защита от перебора: 5 ошибок подряд с одного
  IP → блок на 5 минут (`PANEL_FAILS`).
- `GET /api/state` → текущий список записей + состояние полной блокировки.
  Возвращает `csrf`-токен сессии, который фронтенд обязан прислать в
  заголовке `X-CSRF` на все изменяющие запросы (защита от CSRF).
- `POST /api/toggle {name, enabled}`, `/api/limit {...}`, `/api/reset
  {name}`, `/api/fulllock {now}` — меняют `config.json` напрямую
  (`panel_mutate`), движок подхватит изменения на следующем тике (≤2 с).

Ограничение доступа: `_allowed_ip()` принимает только приватные/loopback/
link-local адреса (через `ipaddress.ip_address(...).is_private`), плюс
правило брандмауэра Windows `HostsBlockerPanel` с `remoteip=LocalSubnet` —
двойная защита, панель физически не отвечает на запросы снаружи домашней
сети. **Это не HTTPS** — пароль и трафик идут открытым текстом в пределах
Wi-Fi. Для чисто локальной сети это принятый компромисс, но при выводе в
интернет (раздел 4) это нужно будет менять на TLS.

### 2.7. Отслеживание активности
Данные собирает агент (раздел 2.3) в `activity_<user>.json`:
```json
{"date": "2026-10-24", "proc": {"chrome.exe": 1532, ...},
 "titles": {"Funny cat video - YouTube": 420, ...}}
```
Секунды по процессам и по заголовкам окон (не по URL — ОС не даёт агенту
доступ к адресной строке браузера без встраивания в сам браузер или чтения
UI через Accessibility/UI Automation API, чего программа не делает — это
следующий шаг, см. раздел 4). Хранится только «за сегодня» (сутки меняются —
счётчики агента обнуляются), истории за прошлые дни нет.

`load_activity()` (вызывается в движке не нужен, используется в GUI) читает
все `activity_*.json` из `PUB_DIR` за сегодняшнюю дату. `top_activity(d)`
отдаёт топ-8 процессов и топ-8 заголовков с фильтром «не меньше 15 секунд» и
чёрным списком системных процессов (`ACTIVITY_SKIP`).

GUI (`activity_dialog()`) показывает это по пользователям, у каждой строки
кнопка «🚫 Заблокировать» → открывает `edit_dialog(None, prefill=...)` с уже
подставленным именем программы (для процессов) или угаданным доменом (для
заголовков — по словарю `BRAND_DOMAINS`, грубый поиск подстроки бренда в
заголовке; работает только для уже знакомых брендов, для незнакомых сайтов
подставится только текст заголовка как название, без домена — пользователю
придётся дописать домен руками).

### 2.8. Блокировка сайтов/программ (базовая, была реализована раньше активности)
Для справки, т.к. остальное строится вокруг этого:
- `apply_hosts(entries)` — переписывает управляемый блок в `C:\Windows\
  System32\drivers\etc\hosts` между маркерами `# >>> HostsBlocker BEGIN >>>`
  / `# <<< HostsBlocker END <<<`, домены → `0.0.0.0` и `::` (IPv4+IPv6).
- `apply_browser_policies(entries)` — пишет групповые политики в реестр
  (`HKLM\SOFTWARE\Policies\...`) для Chrome/Edge/Brave (`URLBlocklist`,
  `DnsOverHttpsMode`, `ProxyMode`) и Firefox (`WebsiteFilter\Block`,
  `DNSOverHTTPS`, `Proxy`).
- `apply_firewall(entries)` — правила `netsh advfirewall` по полному пути
  `.exe` и по IP/CIDR-подсетям (нужно для сервисов вроде Telegram, у которых
  зашитые IP, а не стабильные домены).
- `kill_processes(names)` — `taskkill /F /T /IM <имя>.exe`.
- Лимиты (`default_limit`, `has_limit`, `blocked_now`, `effective`,
  `limit_text`, `in_window`) — у каждой записи может быть лимит минут/день,
  минут всего, разрешённое временное окно; та же модель данных переиспользуется
  для полной блокировки компьютера (раздел 2.5).

### 2.9. Логотипы — без Pillow
Картинки отрисованы один раз Pillow-скриптом (не входящим в сам
`hosts_blocker.py`) и встроены как PNG/base64 в словарь `ASSETS` в конце
файла, в нескольких размерах под разный DPI экрана (от 100% до 300%
масштабирования). В рантайме Pillow не используется и не импортируется —
картинки просто декодируются через `tk.PhotoImage(data=...)`. Для `.exe`
файлов на диске ребёнка (игры и т.п.) логотип берётся напрямую из системы
через WinAPI (`exe_pixels()`, `PrivateExtractIconsW` + `DrawIconEx` +
`CreateDIBSection`), тоже без Pillow. Для сайтов без готового логотипа —
одноразовая фоновая загрузка фавиконки через `google.com/s2/favicons` и
кэширование в `icons/<домен>.png`.

**Если нужно добавить новый бренд/логотип** — дорисовать его придётся
отдельным скриптом (Pillow или вручную PNG) и вставить base64 в `ASSETS`,
либо просто положиться на автоматическую загрузку фавиконки/цветную плитку с
буквой (`_tile`, срабатывает как запасной вариант сам по себе, ничего
доделывать не обязательно).

## 3. Модель данных (`config.json`)

```jsonc
{
  "salt": "...", "hash": "...",              // пароль входа в GUI/панель (PBKDF2-HMAC-SHA256, 200k итераций)
  "seed": 2,                                  // версия списка записей по умолчанию (для миграций при обновлении)
  "child_account": "RaufChild",               // системное имя Windows-аккаунта ребёнка (может быть пустым)
  "full_lock": {"now": false, "daily": 0, "total": 0, "from": "", "to": ""},
  "web": {"enabled": false, "port": 8765},     // веб-панель
  "entries": [
    {
      "name": "YouTube",
      "enabled": false,
      "domains": ["youtube.com", "youtu.be"],
      "programs": [],                          // полные пути или имена .exe
      "ips": [],                                // CIDR-подсети для брандмауэра
      "methods": {"hosts": true, "browser": true, "firewall": true,
                  "kill": true, "noproxy": false},
      "limit": {"daily": 0, "total": 0, "from": "", "to": "", "close_tab": true}
    }
  ]
}
```
`normalize(entries)` при каждой загрузке конфигурации достраивает
недостающие поля значениями по умолчанию — это главный механизм миграции
схемы данных при обновлении программы. **Если добавляешь новое поле записи
— добавляй его в `normalize()`**, иначе старые сохранённые конфиги будут
падать с `KeyError`.

## 4. Что пользователь просил добавить и ЕЩЁ НЕ СДЕЛАНО

Это прямая цитата желаемого функционала из разговора с пользователем,
переданная следующему агенту как ТЗ:

### 4.1. Просмотр экрана ребёнка в реальном времени («онлайн»)
Не реализовано вообще. Для реализации потребуется:
- Захват экрана в сеансе пользователя — **скорее всего через `--agent`**
  (он уже работает в сеансе ребёнка), т.к. движок (SYSTEM) не имеет доступа
  к рабочему столу интерактивного пользователя (Session 0 isolation — та же
  причина, по которой `foreground_info()` вынесен в агента, а не в движок).
  Технически: GDI (`BitBlt` в `CreateCompatibleBitmap`) или Desktop
  Duplication API (`IDXGIOutputDuplication`, даёт лучшую производительность
  и меньше нагрузки на CPU, но сложнее в реализации через голый `ctypes`
  без `comtypes`/`pywin32`).
- Сжатие в видеопоток — сейчас в проекте вообще нет кодирования видео. Сырые
  кадры размером с экран, присылаемые раз в секунду, уже дадут заметную
  нагрузку на диск/сеть при файловом IPC (раздел 2.4) — для этого файловый
  обмен не годится, нужен будет сокет (см. 4.3) или хотя бы localhost HTTP
  MJPEG-поток (проще всего реализовать без зависимостей: JPEG-кодирование
  без Pillow сделать неудобно — скорее всего здесь придётся либо подключить
  Pillow только для этой части, либо писать свой минимальный энкодер, либо
  слать несжатый BMP по локальной сети, что уже не так страшно, раз сеть
  локальная).
- Для показа в веб-панели — вставить `<img>` с обновляемым src или
  MJPEG `multipart/x-mixed-replace` поток, браузер телефона умеет это
  нативно без доп. библиотек на фронтенде.
- Хранить/стримить непрерывно не нужно и не стоит — пользователь просил
  именно «увидеть сейчас», разовый снимок или короткий živой поток по
  запросу, не постоянную запись (постоянная запись экрана ребёнка — гораздо
  более серьёзный по этике и объёму данных функционал, его стоит обсудить с
  пользователем отдельно, не делать по умолчанию).

**Важно для следующего агента**: прежде чем это реализовывать, стоит ещё раз
явно спросить пользователя, нужна ли именно живая трансляция экрана
(существенно увеличивает сложность, нагрузку и риск неправильной настройки
безопасности) или достаточно разового скриншота по кнопке — второе кратно
проще и, вероятно, закрывает 80% запроса «посмотреть, что там сейчас».

### 4.2. Удалённое управление через интернет (не только локальная сеть)
Сейчас веб-панель (раздел 2.6) работает **только в пределах домашнего
Wi-Fi** — это было осознанное и явное решение пользователя («давай только 2
вариант пока что», где вариант 1 — удалённый рабочий стол, вариант 3 —
Tailscale/VPN поверх той же локальной панели). Пользователь попросил именно
п.2 на этом этапе, но в этом сообщении уточнил, что хочет в будущем доступ
«не только по локальной сети, но и через интернет».

Предложенные пользователю ранее варианты (их стоит знать следующему агенту,
чтобы не предлагать заново то же самое с нуля):
1. **Удалённый рабочий стол** (Chrome Remote Desktop / AnyDesk) — не
   требует изменений в коде, работает уже сейчас, но это не «встроенная»
   функция программы.
2. **Веб-панель только в локальной сети** — то, что сделано сейчас
   (раздел 2.6).
3. **Веб-панель + Tailscale** (или аналог, например WireGuard) — панель
   остаётся локальной (как сейчас, код не трогаем), а доступ из интернета
   даёт отдельная установленная программа, создающая приватную
   «виртуальную домашнюю сеть» между телефоном и компьютером. Это
   рекомендованный путь, если нужен доступ из интернета **без
   самостоятельной разработки P2P-протокола** — минимальный риск, не
   требует переписывать `PanelHandler`.

**Пользователь также упомянул «P2P или что лучше, скоростной»** — то есть
рассматривает и вариант написания собственного P2P-протокола (например, на
основе WebRTC data channels со STUN/TURN для обхода NAT). Это на порядок
сложнее варианта 3 и добавляет серьёзную поверхность атаки (открытый в
интернет канал к родительскому инструменту контроля с SYSTEM-правами
движка на одном конце). **Рекомендация следующему агенту**: не
реализовывать самодельный P2P до тех пор, пока:
- не будет отдельного протокола аутентификации сильнее, чем текущий
  пароль + cookie (например, ключи вместо пароля, подпись запросов);
- не будет шифрования канала (TLS/DTLS) — сейчас панель работает по
  голому HTTP, это осознанно допустимо только потому что трафик не
  покидает домашнюю сеть;
- пользователь явно подтвердит, что хочет именно это, а не рекомендованный
  вариант 3 (Tailscale), который даёт тот же результат («управлять из
  любого места») с гораздо меньшим риском и без необходимости писать
  сетевой протокол с нуля в рамках непрофессионального проекта.

### 4.3. Архитектурное следствие для 4.1+4.2
Если решите действительно делать живой экран + доступ из интернета — текущая
файловая архитектура обмена (раздел 2.4) для этого не подходит вообще (это
не про безопасность, а про задержку и объём данных — файлы по 2 секунды не
годятся для видео). Реалистично это означает:
- Добавление постоянного сетевого соединения между агентом/движком и
  клиентом (сокет или HTTP long-poll/WebSocket — `http.server` голого
  Python не умеет WebSocket без ручной реализации рукопожатия, это
  осуществимо но нетривиально; возможно, стоит на этом этапе всё же
  разрешить себе одну внешнюю зависимость, явно предупредив пользователя,
  т.к. требование «ноль зависимостей» было дано в контексте простой
  блокировки/лимитов, а не видеостриминга).
- Отдельный разговор с пользователем о том, что цена сложности сильно
  растёт, и может быть разумно вынести это в отдельный модуль/проект, а не
  доращивать 370 КБ-файл с блокировкой hosts до медиасервера.

## 5. Известные ограничения (сообщались пользователю, учитывай при доработке)

- Аккаунт ребёнка должен быть **обычным пользователем Windows, не
  администратором** — иначе он может сам отключить фоновую службу или
  удалить программу. Это ответственность пользователя (родителя), программа
  это не проверяет и не навязывает.
- Определение сайта в агенте — по **заголовку окна браузера**, не по URL.
  Два следствия: (а) страница с посторонним текстом в заголовке, в котором
  случайно есть «похожее» слово, закроется ошибочно; (б) сайт без
  узнаваемого текста в заголовке не будет обнаружен вообще. Настоящее
  чтение адресной строки потребовало бы Accessibility/UI Automation API —
  не реализовано.
- Файлы в `PUB_DIR` (агент, активность) пишутся с правами обычного
  пользователя и теоретически могут быть удалены/подделаны самим ребёнком
  (см. раздел 2.3) — это не криптографически защищённый журнал.
- Веб-панель — только локальная сеть, без TLS (раздел 2.6, 4.2).
- `full_blocked`/`apply_full_lock` — код написан, но **ни разу не
  тестировался на настоящей Windows** (ни `net user`, ни
  `WTSLogoffSession`, ни поведение при разных языках системы, где вывод
  `net user` может быть в другой кодировке — для этого есть
  `_console_decode()` с перебором `cp866/cp1251/utf-8`, но это тоже не
  проверено вживую).
- Нет истории активности за прошлые дни — только «сегодня».
- Межпроцессный обмен — через файлы, не атомарен на уровне
  «читать-изменить-записать» между разными процессами (есть блокировка
  только внутри процесса панели — `PANEL_LOCK`). Два одновременных
  изменения (например, с телефона и в открытом диалоге на компьютере)
  могут привести к тому, что одно перезапишет другое. GUI частично
  смягчает это, перечитывая конфиг с диска каждые 15 секунд, если в этот
  момент не открыт диалог редактирования.

## 6. Как это тестировалось (и как тестировать дальше)

**Нет доступа к Windows** в среде, где писался код — поэтому всё, что
трогает реальные Windows API (реестр, `net user`, `WTSLogoffSession`,
`netsh`, иконки `.exe`, DPI) **не выполнялось по-настоящему**, только
прошло проверку `python3 -m py_compile` (синтаксис корректен) и, где
возможно, логическое юнит-тестирование: модуль `tkinter` подменялся
фиктивными заглушками (`sys.modules["tkinter"] = types.ModuleType(...)`),
после чего вызывались и проверялись **чистые функции** — те, что не требуют
реального окна или реальной Windows: `full_blocked`, `full_lock_text`,
`in_window`, `blocked_now`, `effective`, `limit_text`, `parse_ips`,
`load_activity`, `top_activity`, а также логика `engine_tick()` целиком —
с подменой (`monkeypatch`) функций, реально трогающих систему
(`apply_all`, `running_names`, `kill_processes`, `apply_full_lock`), на
функции-пустышки, которые просто записывают, что их вызвали, с какими
аргументами.

Веб-панель тестировалась по-настоящему: `http.server` кросс-платформенный,
поэтому `panel_start()` реально поднимался на `127.0.0.1` в Linux-песочнице,
и к нему шли настоящие HTTP-запросы (`urllib.request`) — проверялись вход,
CSRF, лимит попыток входа, переключение записей, лимиты, сброс счётчика,
переключатель полной блокировки, содержимое HTML/JS.

**Что нужно будет проверить на реальной Windows-машине** (чеклист для
следующего агента или для пользователя):
1. Сборка exe через PyInstaller без `--uac-admin`, UAC-диалог появляется
   сам при запуске.
2. Установка задач планировщика (`schtasks`), что `HostsBlockerEngine`
   реально стартует при перезагрузке от SYSTEM.
3. ACL на `C:\ProgramData\HostsBlocker` и `...Pub` — что обычный
   пользователь не может прочитать первую и может писать во вторую.
4. `net user <имя> /active:no` и последующий `WTSLogoffSession` — реально
   ли это рвёт сеанс ребёнка и блокирует повторный вход.
5. Правило брандмауэра для веб-панели (`remoteip=LocalSubnet`) — что с
   телефона внутри Wi-Fi панель открывается, а с внешнего IP — нет.
6. DPI/логотипы на экранах с масштабом, отличным от 100%.
7. Закрытие вкладки (`Ctrl+W` через `keybd_event`) в разных браузерах —
   может не всегда работать, если фокус не на вкладке, а например на
   диалоговом окне браузера.

## 7. Стиль кода и соглашения, которых стоит придерживаться

- Все тексты интерфейса — на русском (пользователь общается по-русски).
- Все пути/реестр/файрвол — только через `IS_WIN` и `run_hidden()` (тихий
  вызов subprocess, без консольного окна, `creationflags=NO_WINDOW`).
- Любая запись конфигурационных/статусных JSON-файлов — через
  temp-файл + `os.replace()` (атомарность), см. раздел 2.4.
- Новое поле в записи (`entries[i]`) — всегда добавлять дефолт в
  `normalize()`.
- Новая настройка верхнего уровня `config.json` — читать через `cfg.get(key)
  or <default>` везде, где используется (как сделано для `web` и
  `full_lock`), не полагаться на то, что поле обязательно есть (старые
  конфиги могут быть без него).
- Если добавляешь вкладку/кнопку в GUI — паттерн `self.button(parent, text,
  cmd, bg=..., fg=...)`, диалоги — `tk.Toplevel`, `pad = {"padx": S(22)}`,
  функция `S(v)` масштабирует под DPI экрана, обязательно использовать её
  для любых новых размеров/отступов (иначе интерфейс снова станет «мутным»
  на экранах с масштабом ≠100%, из-за чего и была отдельная переделка).
- Если добавляешь эндпойнт в веб-панель — обязательно проверка `X-CSRF` для
  изменяющих запросов и `_allowed_ip()` уже встроена на уровне
  `do_GET`/`do_POST`, трогать не нужно.
